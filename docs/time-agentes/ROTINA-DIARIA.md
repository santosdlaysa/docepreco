## Execução

1. Confira data local, estado do Git, fontes acessíveis e o último relatório. Preserve alterações existentes. Não use números antigos como atuais.
2. Leia BASE.md e os perfis das áreas. Abra os prints em `marketing/telanovaapp/` quando a tarefa envolver visual, navegação ou conteúdo do app. Este é o nome real da pasta mencionada pela usuária como telasnovaapp. Não deduza a tela apenas pelo nome do arquivo. Prints não comprovam sozinhos a regra de plano ou publicação de uma função.
3. Defina uma demanda concreta para cada área com objetivo e critério de conclusão. Trabalhe com até três especialistas em paralelo se houver ferramenta de delegação; cada frente pode assumir perfis em sequência. Se indisponível, execute sequencialmente e informe a limitação.
4. Produza uma entrega útil por área ou identifique um bloqueio real. Não invente falhas, alterações de código, métricas ou atendimentos para preencher o relatório. Se a revisão não encontrar problema, registre o resultado e a evidência.
5. Teste as alterações com verificações adequadas. Não aplique migrações em produção para testar. Registre testes executados, resultado e limitações. Banco/admin só em leitura autorizada, com TLS verificado, timeout e transação somente leitura; não imprima credenciais nem exporte dados pessoais.
6. Salve em `docs/time-agentes/entregas/diario/AAAA-MM-DD/`. Gere `RESULTADO.md` com as oito áreas, suas entregas, estados, testes e pendências. Na mesma data, retome pendências em vez de produzir duplicatas. Relatórios são arquivos do projeto, não resultados de negócio presumidos.

## Limites da produção

Produza uma peça principal escrita por rodada e poucas variações úteis, evitando repetir todo o catálogo. Novas imagens só quando necessárias ao objetivo e após conferir as já existentes; use geração de imagens para criação/edição visual. Vídeo só pode ser declarado pronto se um arquivo de vídeo foi realmente produzido e verificado. Não gerar imagens nem rodar testes amplos repetidos apenas para ocupar todos os agentes.

Pode realizar melhorias locais pequenas e justificadas no código, preservando escopo e alterações alheias. Não iniciar funcionalidades grandes, alterar cobrança/acesso, publicar, implantar, enviar push/WhatsApp/e-mail, fazer push Git ou EAS update por este agendamento. Materiais de contato ficam preparados para revisão; envios dependem de instrução da usuária para a ação/rotina específica. Se houver acesso ausente, informe o bloqueio; não simule execução nem prometa que o computador estará disponível no próximo horário.
